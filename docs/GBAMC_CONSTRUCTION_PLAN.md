# GBAMC 基准构造方案（供审核，不直接生成数据）

目标：用**真实、可追溯来源**构造“粤港澳大湾区医疗合规”测试集（GBAMC），使
LexMedRAG 论文的实验数据可复现、可核查。本文件只给方案与来源，不产生任何
“拍脑袋”的 600 条查询。

## 1. 数据源选型（按真实性与可得性排序）

| 来源 | 内容 | 访问方式 | 许可/限制 | 适用性 |
|---|---|---|---|---|
| MIMIC-IV | 真实 ICU 电子病历（成人，约 7 万例） | PhysioNet，需完成 CITI 培训并签署 DUA | 受限、禁止再分发；只允许在授权环境内使用 | 最高真实性；须在授权机器上本地派生属性集 |
| MIMIC-IV Demo | 公开演示子集（约 100 例） | PhysioNet 直接下载 | 接受简单数据使用协议即可 | 管线联调、格式验证 |
| eICU | 真实重症数据 | PhysioNet，同样需凭证 | 受限 | 备选 |
| Synthea | 开源合成患者生成器（Apache-2.0） | GitHub + 官方样例输出 | 开放、无真实 PHI | 首选“无凭证”路线；人口学/诊断/处方字段真实合理 |
| 国家/省级公开统计 | 卫生统计年鉴、广东健康医疗数据相关公开文件 | 官方网站 | 公开 | 用于人口学与疾病分布校准 |

**已定路线（2026-09 决策）：无凭证的 Synthea**。产出字段仍须与本项目
`data/` 中的属性本体（见 `knowledge_utils.py` 的医学数据分类背景）及
《广东省健康医疗数据安全分类分级管理技术规范》的分级规则对齐。

### 0. 运行步骤（Synthea 路线）

1. 安装 Java 17+，下载 Synthea 发行包或克隆
   `https://github.com/synthetichealth/synthea`；
2. 生成合成人群并导出 CSV（种子固定，保证可复现）：
   `java -jar synthea-with-dependencies.jar -p 2000 -s 20260909`
   （输出位于 `output/csv/`：patients.csv、conditions.csv、
   observations.csv、medications.csv 等）；
3. 在本项目根目录运行：
   `python -m gbamc.generate_queries --synthea <output/csv> --per-scenario 120`
   生成 600 条（5 场景 × 120）草稿查询到 `results/gbamc_queries_draft.json`；
4. 审核 `gbamc/attribute_map.py` 与 `gbamc/scenarios.py`（第一稿），
   定稿后重新生成正式 GBAMC。

管线已用测试夹具做过冒烟验证（10 条草稿，仅用于流程检查，
见 `results/gbamc_queries_smoke.json`，不作为正式数据）。

## 2. 属性映射（真实规则的锚点）

1. 从数据源抽取字段：诊断 ICD-10、处方/用药、检验、基因/生物样本标记、人口学、
住院号/病历号等；
2. 按知识库本体映射到语义类别：个人属性数据、健康状况数据、医疗应用数据、
医疗支付数据等；
3. 按 GDHMD 规则（`CN_GDHMD_*`，来自 `legal_knowledge_base.json`）映射到
1–4 级与跨境措施（匿名化/脱敏、影响评估、国家审批等）；
4. 输出映射表 `attribute_map.csv`：字段→本体类别→分级→相关 rule_id，供审核。

## 3. 五类跨境场景（与论文一致）

1. HK 医院 → 内地 AI 公司（诊断模型训练，基因/影像/病历）；
2. 澳门医院 → 深圳机构（多中心试验，检验/基因数据）；
3. 内地研究机构 → 香港药企（药物警戒/统计）；
4. 大湾区医院集团内部跨境（远程诊疗、转诊）；
5. 港澳机构 → 内地数据中心（存储/灾备，含可穿戴数据）。

每个场景给出：场景说明、参与主体、法域流向、动作类型、数据规模分布
（如 100–10 万条）、时间范围——参数表由你审核确认。

## 4. 查询模板（与论文定义 1 一致）

每条查询为 `Q = (X_target, C_op)`：

```json
{
  "query_id": "GBAMC-0001",
  "scenario": "hk_to_cn_ai_training",
  "X_target": ["icd10", "hospital_id", "genomic_variant"],
  "C_op": {"loc_src": "HK", "loc_dst": "CN", "act": "model_training",
           "vol": 50000, "t": "2024-11-15"}
}
```

## 5. 法律覆盖与 gold 冲突对（关键步骤）

现有 72 条规则**只覆盖内地**，且同一法域、经整理的规则之间“同场景真正冲突”
极少（pilot 初判已证实）。构造 CRR gold 必须：

1. 扩充规则库：从**官方原文**（如香港个人资料私隐条例、澳门个人资料保护法、
大湾区个人信息跨境流动标准合同/备忘录）抽取规则，沿用
`legal_knowledge_base.json` 的 schema，并补 `region/效力层级/义务模态/适用条件`；
2. 在**查询条件化**的前提下标注冲突：对每条抽样查询列出其适用规则集合，
由标注者判定哪些规则对构成冲突（许可与禁止、义务与许可、一般与例外、
强制与可选）并给出压制/排除结论；
3. 风险 gold：由两位以上具备医疗数据合规背景的标注者独立评分（0–1），
不一致处讨论收敛；
4. LV/BU：按论文口径取 n=300 专家评分样本（而非 n=20 LLM 标注）。

## 6. 生产步骤（每步产出可审核文件）

1. 数据源获取与清洗（记录来源、版本、日期、授权证明）；
2. 合成/派生人群与字段抽取（种子固定，保证可复现）；
3. 属性映射表审核 → 定稿；
4. 场景与参数表审核 → 生成 600 条查询（分 5 场景 × 120）；
5. 规则库扩充（含港澳法条原文链接与日期）→ 审核；
6. 抽样标注（冲突/风险/LV/BU）→ 专家审核 → 形成 `gold/` 正式文件；
7. 评测脚本在**正式 gold** 上运行，产出可复现结果。

## 7. 底线

- 不编造查询、不编造标注、不把 pilot/草稿数字写进论文；
- 真实 MIMIC 数据只在授权环境处理，任何可发布文件不得含可识别个人信息；
- 每个可审核文件都带来源与日期，便于追溯。
